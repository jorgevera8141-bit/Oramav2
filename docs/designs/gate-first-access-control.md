# Design: Gate first, then per-person login (orama-v2 access control)

Generated by /office-hours on 2026-10-02
Branch: main
Repo: jorgevera8141-bit/Oramav2
Status: APPROVED
Mode: Startup

## Problem Statement
Every `/api` route in orama-v2 (90 routes, plus `/health`) can be called without a login, at a public address, and the GitHub repo is public with that address in `src/shared/notify.js`. Anyone can read payroll, change menu prices, delete records and stamp invoices. Per-action PINs cover only some money-moving actions (comps, loyalty redemption, approvals).

## Demand Evidence
None gathered; the stage is "has users" for an internal tool, so the routing skipped Q1. Pain so far: no incident reported ("Per-action PINs + trust, no incident"). Exposure evidence: public repo plus live URL. The Railway request logs have not been checked for unfamiliar callers (step 0 below).

## Status Quo
An open app, per-action PINs on a few actions, and trust in staff.

## Target User & Narrowest Wedge
Users are the café's cashiers, baristas and managers on a shared counter tablet, phones and a wall-mounted bar display. No individual named. Wedge: a café-wide gate (one shared passcode, HTTP Basic Auth) in front of the app shell and the API, on a deny-by-default skeleton. Roles are not part of step one.

## Constraints
- **Public allowlist (committed, pinned by a test):** `GET /health` (Railway health check); `/loyalty.html` with exactly the static files it loads (`/css/orama-pro.css`, `/css/orama-loyalty.css`, `/js/orama-fx.js`, `/js/orama-loyalty.js`); `GET /api/loyalty/customers/:phone` and `POST /api/loyalty/customers`. These return only id, phone, nombre and the stamp card, and are rate limited (60 lookups per 10 minutes, 20 signups per hour per address, since PR #15). Accepted residual risk: anyone who knows a phone number can see that person's name and stamp balance.
- **Everything else is gated:** the app shell (`/`, `/index.html` and its scripts and styles), `/uploads`, and every other API route.
- **Credential mechanism (committed):** HTTP Basic Auth with the passcode as the password and any username. The browser shows its own prompt, so there is no new screen and no client code change; once the shell loads, every same-origin `fetch` carries the credential. Browsers cache it per browsing session (a password manager can save it), so devices re-prompt after the browser is closed; this is a trade accepted for the one-day scope.
- **Bar display:** a person signs it in once when it is installed or restarted; its polling (every 30 seconds) then keeps working. A dead credential makes it stop updating until someone answers the prompt; the "Pantalla desconectada" banner from the saved design (decision 15) belongs to step two.
- **Machine and streaming callers (verified in code):** none. There are no WebSocket, SSE, webhook or cron endpoints; every integration (Telegram, ntfy, Facturapi, 9Router, fal) is outbound from the server. The bar display and dashboard poll with `fetch` every 30 to 60 seconds.
- Staff have not been observed during a rush (Q5: "No, not yet"), so the per-person login design was sized from the code, not from watching.

## Premises
1. The first problem is strangers (anyone with the URL can read, change, delete); per-person accountability is second.
2. Nothing visibly went wrong, but "nobody has looked" is unverified; real exposure exists regardless.
3. A café-wide gate fixes the stranger problem with no new screens (the browser's native prompt), leaving the allowlist above open.
4. The per-person login (28 design decisions) is the right long-term fix, sized after watching a real rush.
5. Doing nothing leaves payroll, prices and invoices open to the internet.

## Approaches Considered
- **A: bare gate.** Ruled out: throwaway work and no safety net for routes added later.
- **B: per-person login as designed.** Deferred until after the gate and an observation session. Saved plan: `~/.gstack/projects/jorgevera8141-bit-orama-server-/designs/login-screen-20261001/login-plan.md`. In short: name-tile and six-digit keypad login, scrypt-hashed PINs, 12-hour sessions with a 3-minute idle lock, manager roles, a paired bar display and in-place manager overrides (10 tasks, 28 design decisions, design score 8/10).
- **C: gate on a deny-by-default skeleton.** Chosen.

## Recommended Approach
**C.** Step zero, before or alongside the build: review the last 30 days of Railway request logs for callers outside the café on `/api/staff*`, `/api/factura*`, `/api/reportes*`, `/api/finanzas`, `/api/settings` and any POST, PUT or DELETE. What changes the plan: an unfamiliar write call means treat it as an incident (audit data, rotate the passcode and staff PINs, bring per-person login forward); only unfamiliar reads mean the gate is urgent but nothing needs rotating, because no route returns a PIN and the database and API keys are not in the repo.

Step one deliverable:
1. A middleware denies every request unless it matches the allowlist or carries the passcode. The secret is `GATE_PASSCODE` in a Railway variable, compared in constant time, with an optional `GATE_PASSCODE_PREVIOUS` so a rotation can run both for a window. It fails closed in production when no passcode is set. Failed attempts are throttled by the existing limiter keyed on `req.ip` (trust proxy is already set for Railway), loose enough that one fumbling person on the shared café connection is slowed, not locked out.
2. Classification is two classes only: public or gated. Role-by-route is per-person-login work and is deferred; nothing in step one needs it.
3. A test enumerates every route through Express's own router (probe on the current app: 91 routes found), requests each without the credential and asserts 401 except for the pinned allowlist. A new route is gated automatically; adding to the allowlist requires a deliberate test change.

Per-person login later swaps what the middleware checks (passcode to session) and adds a role column to the same classification.

Time: about one day is the working estimate. The unverified part is how Basic Auth behaves on the real iOS and Android browsers, the home-screen app and the bar tablet, which only trying it will show.

## Open Questions
1. How does Basic Auth behave on the café's actual devices (iOS Safari including a home-screen app, Android Chrome, the bar tablet)? If it is unusable, the fallback is a cookie set by a one-field passcode form.
2. Who holds the passcode, and who rotates it? A leak is handled by setting `GATE_PASSCODE` to a new value (and `GATE_PASSCODE_PREVIOUS` to the old one for a window); every device then re-enters it, including the bar display.
3. What triggers step two? Revisit after the observation session, at 30 days after the gate ships, or immediately on any incident (a staff member misusing access, or a leaked passcode).

## Success Criteria
- Every route except the pinned allowlist returns 401 without the passcode (all 91 routes, by test).
- The loyalty page still looks up and signs up customers from a phone with no passcode.
- With the passcode entered once per browser session, the counter tablet, phones and the bar display work; checked on the real devices.
- During a rotation both passcodes work, and after the old one is removed it returns 401.
- A route added without touching the allowlist is gated automatically.

## Dependencies
A Railway environment variable; access to the Railway request logs; the saved login plan and its design review as the step-two follow-up.

## The Assignment
Sit behind a cashier for one full rush (20 to 30 minutes) without helping, and write down three things they did that you did not expect. Notice especially whether anyone shares a device, what the bar screen shows, and what happens when someone meets a PIN prompt.

## Reviewer Concerns

### R2-1 — completeness

**Problem**

> The failed-attempt throttle is only described as 'loose enough that one fumbling person on the shared café connection is slowed, not locked out'. No limit, window or lockout behavior is given, so the committed behavior cannot be tested or reviewed. Success Criteria do not cover throttling at all.

**Remedy**

> State the numbers (for example N failed attempts per window per req.ip), what the response is when exceeded (429 with Retry-After, or delay), whether a correct passcode is still accepted while throttled, and add a success criterion for it.

### R2-2 — feasibility

**Problem**

> The deny-by-default test enumerates routes 'through Express's own router (91 routes found)'. Static files and the app shell (`/`, `/index.html`, scripts, styles, `/uploads`) are normally served by express.static middleware, which does not appear in the router route list, yet they are committed as gated. The test as described may not cover them, and exact-match allowlist handling of trailing slashes, case, encoded or dot-segment paths, HEAD and OPTIONS is unspecified.

**Remedy**

> Specify that the middleware is mounted before express.static and the test also probes the shell, static directories and `/uploads` plus path variants and HEAD/OPTIONS against the allowlist, and say how a newly added static directory is caught.

### R2-3 — completeness

**Problem**

> Browsers send some requests without cached Basic Auth credentials, notably the web app manifest, home-screen app launches and service-worker or icon fetches. The document names the iOS home-screen app only as an unverified question; if the manifest or icons return 401 the home-screen app may fail to install or start, and the document does not say whether any of these are allowlisted.

**Remedy**

> Inventory the manifest, icons and any service worker the shell loads and decide for each whether it is allowlisted (and added to the pinned test) or gated, and what the home-screen app does on a 401.

### R2-4 — clarity

**Problem**

> The committed mechanism (Basic Auth, 'no new screens', 'about one day') depends on Open Question 1, and the fallback (cookie plus a passcode form) is a new screen and more work that contradicts Premise 3. The document does not say the device check happens first or what outcome switches the approach, so committed behavior and discovery are mixed.

**Remedy**

> Add an explicit first step: a short spike of Basic Auth on the real devices (iOS Safari, home-screen app, Android Chrome, bar tablet) before the build, with the pass/fail criterion and the re-estimate if the fallback is chosen.

### Prior finding evidence

**R1-8 → R2-1 (persisting)**

> Credential persistence is now specified (browser-session cache, re-prompt after close) and the limiter is keyed on req.ip with trust proxy set, but the lockout behavior for legitimate staff is only 'loose enough', with no values.
